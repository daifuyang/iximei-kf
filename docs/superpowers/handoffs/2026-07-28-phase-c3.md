## 4. Fix Round 原因 + 解决方式

### 4.1 T2 fix round（commit `220c311`）

**原因**：plan §5.1 字段映射写法是 backend 形态（`(stats as any)?.hospitalRankings?.items ?? []`，并假定前端 `HospitalRankingItem` 的字段名就直接是 `hospitalId`/`hospitalName`/`dispatchCount`/`viewedRate` 等）。但 Phase B 已落地的 UI 形态是：

```ts
// apps/yishan-admin/src/modules/crm/pages/dashboard/types.ts:124-131
export type HospitalRankingItem = {
  rank: number
  name: string
  dispatchCount: number
  arrivalRate?: number
  conversionRate?: number
}
```

直接照搬 plan §5.1 会让 UI 表的 `name`/`rank`/`arrivalRate` 全 undefined（仅 `dispatchCount` 列能显示数字）。

**解决**：T2 implementer 主动 escalate，orchestrator 给 Ruling A（utils.ts 内做适配）：

```ts
// utils.ts:395-421
return items.map((it, idx) => ({
  rank: idx + 1,                                    // backend 已 ORDER BY dispatchCount DESC
  name: it.hospitalName,                            // rename: hospitalName → name
  dispatchCount: it.dispatchCount,
  arrivalRate: it.viewedRate,                       // 最近可量化代理（spec §0 已注明）
  conversionRate: undefined, // TODO: C.3.2 follow-up
}))
```

**亮点**：subagent 严格按「不照搬，主动 escalate」约定，省了 reviewer 抓回的 round trip。✅ Re-review ADDRESSED, Approved（task-2-re-review §5）。

## 7. C.3 follow-up（建议后续 ticket，不阻塞）

按 spec §1 与 §6 声明路线：

### 7.1 筛选维度（spec §1 / 路线 1：「C.3.1 跨医院对比实时推送」、「按品类 / 区域」）

- **C.3.1.1 排行筛选维度**：按品类 / 区域 / 时间段 —— 后端新增 query params；前端 ProForm 控件（已熟悉的 Selection/Select）；后端 SQL WHERE 条件动态拼接。**预计 2-3 task**（后端 schema + repo + service + route + 前端 form + 适配）。
- **C.3.1.2 跨医院对比实时推送**：需 SSE / WebSocket，**FC 不支持**长连接。两种降级：(a) 改用更密集的轮询（60s→10s），加 server ETag 304；(b) 阿里云 FC3 HTTP 触发器 + 函数间调用，最差保留轮询。**预计需独立 spec 评估可行性**。

### 7.2 历史快照（spec §6「C.3.3 排行历史快照」）

- **C.3.2 历史快照**：昨天/上周/上月排行 —— 后端需要 snapshot 表（`crm_hospital_ranking_snapshot`，含 `snapshot_date` + `rankings_json` + `generated_at`）+ 定时任务（每日 00:05 cron，FC 定时触发器）+ 前端时间选择器。
- **数据库迁移**：crm 模块新增 1 张表；permission 加 `crm:dashboard:ranking-history:view`。
- **预计 3-4 task**（schema 迁移 + 定时器 + API + 前端）。

### 7.3 conversionRate 真实业务字段（任务 2 follow-up §6）

- 后端 metric 缺失：当前 `HospitalRankingItem.conversionRate` 列恒显 `--`。**C.3 范围内无成交率字段**（crm_dispatch_followup / crm_dispatch_reply 不足以推算）。建议 C.3.3 业务 ticket：在 CRM 模块加 `crm_dispatch_conversion`（dispatch_id → converted_at + converted_amount + converted_by_user_id），后端聚合时 JOIN；前端 `conversionRate` 列从 `--` 变实际百分比。
- 也可降级：原删 `conversionRate` 列（避免 UI 永久 `--`），后续有 metric 再加回。

### 7.4 数据范围过滤（task-1-review §F5）

- `hospital_account` 角色当前看到所有医院聚合数据（潜在越权）。**不在本 spec range**；需产品决策（"全院 CRM 数据看板" vs "仅可见医院"）后单独立规。

### 7.5 openapi.json 双胞胎路径清理（task-1-review §N1）

- `/api/crm/v1/dashboard/dashboard/stats` 是历史 stale artifact（重复路径）。下次 openapi.json 相关 sprint 顺手删 stale 重复段。本次不打 patch（避免越界）。
